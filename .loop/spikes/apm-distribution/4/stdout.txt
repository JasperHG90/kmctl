Rules for writing knowledge:
- audience-picks-the-folder: docs/ is for people who use the project; .okf/ is for people and agents working on it. A decision, proposal, prototype, audit or handoff goes in .okf/, even when it reads like a guide.
- docs-sorted-by-reader-intent: Each docs/ page has one Diataxis type: tutorials/ (a lesson that works in one sitting), how-to/ (one task, one way), reference/ (facts, no instructions), explanation/ (why it is shaped this way). Two intents in one page means two pages.
- docs-describe-what-exists: A docs/ page lands in the same change as the behaviour it describes. Until then the design lives in .okf/.
- prototypes-hold-their-scripts: A prototype is one folder in .okf/prototypes/ with its README.md, every script behind a number in it, and the raw results. Never run analysis inline or from a scratch folder.
- start-at-the-index: Start at .okf/index.md and follow links. One concept is one file, named in kebab-case for an entity, never a change. Prefer updating a concept to adding a neighbour.
- kmctl-writes-the-structure: Create concepts with kmctl new; it writes front matter, the index entry and the log line, and you write the prose. After any hand edit to an index, run kmctl check.
- every-touched-concept-is-logged: A change that touches a concept appends a dated line to .okf/log.md naming its id in backticks. Never rewrite an earlier line.
- decisions-are-never-rewritten: Record a decision when it is made, with the alternative it rejected. Correct it with an appended dated section; reverse it with a new record that supersedes it.
- trust-is-recorded: An agent records itself in generated.by and leaves the concept unverified. Only a person who checked the content adds a verified entry. Treat unverified or stale concepts as leads, not facts.
